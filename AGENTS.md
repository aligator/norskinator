# AGENTS.md

Norskinator — static Vite + Lit + TypeScript app for drilling Norwegian (bokmål)
grammar with spaced repetition. No backend logic, state lives in localStorage.
It ships as a Docker image: `dist/` served by nginx (`Dockerfile`,
`docker/nginx.conf`).

## Commands

```bash
pnpm install          # pnpm only, never npm/yarn
pnpm run dev          # vite dev server
pnpm run verify       # typecheck + tests + build
pnpm run data         # re-download Tatoeba and regenerate the exercise bundle
```

## Code style

Hard rules, enforced in review:

1. No one-line `if`. The body goes on its own line.
2. Never an `if`/`for`/`while` without braces.
3. Group statements with blank lines; a wall of code without breaks is a bug
   report waiting to happen.
4. Comment a group only when the comment adds information. A comment that
   restates the code must be deleted.
5. No single-letter identifiers.
6. TypeScript only, `strict` plus `noUncheckedIndexedAccess`. No `any`.
7. Core logic (`src/core/`) stays framework-free so it is testable without a
   DOM. Lit is only used in `src/ui/`.

## Architecture

- `src/core/` — domain types, task types, SRS, gamification, session
  building, storage, store, stats. Pure and unit-tested.
- `src/decks/` — content. One folder per topic, registered in
  `src/decks/registry.ts`.

- `src/ui/` — Lit, in three layers:
  - `components/` — generic UI building blocks (progress ring/bar, segmented
    control, stepper, switch, icons, design tokens). **No imports from
    `core/`, `decks/`, `modules/` or `pages/`.**
  - `modules/<area>/` — domain components and UI logic per area
    (`practice`, `gamification`, `decks`, `stats`, `settings`, `shared`).
    May use `core/` and `components/`, never `pages/`. Navigation is
    requested through events (`exit`, `session-started`), not done directly.
  - `pages/` — `app-root` (shell, nav, routing, theme, live region) and one
    thin page per route that composes modules.
- `scripts/` — build-time data pipeline (`tsx`), never shipped to the browser.
- `tests/` — cross-cutting tests that need Node (`tests/ui-architecture.test.ts`
  enforces the UI layering above).

`tsconfig.json` covers `src/` without Node types; `tsconfig.node.json` covers
`scripts/`, `tests/` and `vite.config.ts`.

### Data, task types and decks

Content and presentation are separate (`src/core/types.ts`):

- A **data item** has a `DataKind`: `cloze` (sentence with one gap, answer,
  `alternatives` that are also correct, `distractors`, optional `hint`) or
  `sentence` (a whole sentence, its word `tiles`, other correct orders as
  `alternatives`).
- A **task type** (`src/core/tasks.ts`) turns an item of one data kind into an
  `Exercise`: `multiple-choice` or `type-in` for cloze, `word-order` for
  sentences (`TASK_DATA_KIND` in `types.ts`).
- A **deck** is a list of sources, each a pool of items plus the task types
  it is practised with. `loadDeck` checks that they fit.
- SRS history belongs to the item, not the task type. Each presentation picks
  a task type by the learner's `taskWeights`: shares within one data kind,
  always 100 % per data kind (`src/core/task-weights.ts`).

The preposition deck has two pools:

- `authored.json` — sentences written with AI for this app, in template form:
  an entry is one sentence, or a pattern with a `{slot}` and `fillers`. Every
  sentence carries its permanent id, translations and alternatives.
  `content.test.ts` validates it.
- `tatoeba.json` — generated by `pnpm run data`, never edited by hand.
  `overrides.json` adds reviewed alternatives, AI translations and
  exclusions on top, keyed by item id.

The adjective deck has one pool, `tatoeba.json` (generated) plus
`overrides.json`, which can also replace an item's `tags` and set its
`explanation`. Each item carries a `hint` (the dictionary form, «stor»), shown
in the empty gap and as the type-in placeholder. Its first tag is a form
category from `categories.ts`, the second `type:<inflection>`.

The word-order deck has one pool of `sentence` items, `tatoeba.json` plus
`overrides.json`. The learner sees the translation and orders the shuffled
tiles; its first tag is a rule from `categories.ts`.

`src/decks/tatoeba-source.ts` maps a generated bundle to items for all three
decks: a bundle item with `options` becomes a cloze item, one with `tiles` a
sentence item.

### Updating corpus data (Tatoeba → deck)

Tatoeba sentences reach a deck in four steps. Agents doing this again follow
them exactly; never hand-edit `tatoeba.json`.

1. `pnpm run data` downloads the exports into `.cache/` and regenerates every
   deck's `tatoeba.json` (`scripts/build-<deck>.ts`, shared reading in
   `scripts/tatoeba.ts`). Ids are `t<tatoeba id>`, so a sentence keeps its id
   across runs; new sentences simply have no review yet.
2. `pnpm run review:export <deck>` writes every item without an entry in the
   deck's `overrides.json` into `.cache/review/<deck>/batch-<n>.jsonl`, plus a
   ready prompt `prompt-<n>.md` per batch (templates in
   `scripts/review/prompts/`).
3. Start one reviewer agent per `prompt-<n>.md`, all in parallel. Each writes
   `out-<n>.jsonl`: exclusions, extra correct answers, missing German/English
   translations and, per deck, category and explanation.
4. `pnpm run review:merge <deck>` validates the output (unknown ids,
   duplicates, invalid categories abort the merge) and writes one entry per
   reviewed item into `overrides.json`, an empty `{}` when nothing changed.
   Then `pnpm run verify`: the deck tests fail while any sentence is
   unreviewed, uncredited or untranslated.

A new corpus deck needs a generator script, an entry in
`scripts/review/decks.ts` and a prompt template.

### Adding a topic

1. Create `src/decks/<topic>/index.ts` exporting a `Deck` with its sources.
2. Add it to `DECKS` in `src/decks/registry.ts`.

Nothing else changes: scheduler, stats and UI are deck-agnostic.

### Adding a question format (task type)

1. Extend `ExerciseKind`, `EXERCISE_KINDS` and `TASK_DATA_KIND` in
   `src/core/types.ts`, and add the exercise shape to `Exercise`. A new shape
   of content also needs a `DataKind` and its item type in `DataItem`.
2. Add it to `TASK_TYPES` in `src/core/tasks.ts` (data kind, label, builder).
3. Handle the new case in `src/core/checker.ts`, and in the store's and
   resume's options handling if it shows choices.
4. Render it in `src/ui/modules/practice/exercise-card.ts`.
5. Give it a share in `DEFAULT_TASK_WEIGHTS` (`src/core/task-weights.ts`);
   the shares of one data kind add up to 100.

TypeScript's exhaustiveness checks point at every spot that needs work.

## Updates and stored data

The app is a PWA (`registerType: 'prompt'`). A new image is downloaded in the
background; `src/ui/modules/update/` shows "Oppdater" outside practice and
checks for updates hourly. Users' progress lives only in their browser's
localStorage, so every deploy must keep it readable:

- **Exercise ids are permanent.** SRS history is keyed by them
  (`p-curated-<id>`, `p-tpl-<template>-<filler>`, `p-t<tatoeba id>`,
  `a-t<tatoeba id>`, `w-t<tatoeba id>`). Never reuse or renumber an id; removed exercises are
  simply ignored.
- **Additive changes** (new optional field): give it a default in the
  `parse*` function in `src/core/storage.ts`. No version bump.
- **Breaking changes** (rename, restructure, changed meaning): bump
  `STATE_VERSION` and add a step to `MIGRATIONS` that upgrades raw data from
  the previous version. Add a test with old data.
- A build that finds data from a *newer* version stops saving
  (`newerVersionStored`) and asks for a reload, so an old tab never overwrites
  newer data.
- localStorage keys (`norskinator.state`, `.session`, `.seenBadges`,
  `.tourDone`) are permanent once released: renaming one wipes every
  learner's progress unless a migration copies the old key first.
- The running session is stored separately (`norskinator.session`) and resumed
  after a reload.
